# Render performance, October 2026

Owner: Noa · Base: `main` @ 3e5f5b7 + the fixes on `dev/noa/perf`.

**Summary.** One bug made `#sports` take **1.8 s** to render on a throttled phone-class CPU. Every other route was
10–65 ms. The cause was building a new `Intl.DateTimeFormat` on every `today()` call, inside a sort comparator. After
the fixes, every main route renders in **under 10 ms** at 4x CPU throttling, except `#calendar` (32 ms, mostly HTML size).
Tripling the data adds at most 2x.

## Method
- **Node:** `node tests/bench.js 1 3` runs the real `site/*.js` in a vm with the smoke tests' DOM stub, and times
  `route()` (median of 15 runs after 3 warm-ups).
  - **Clock:** pinned to 29.10.2026, Abu Dhabi day 1, so the strip, `#day` and `#c-` all have content.
  - **Data:** the fixture (99 athletes, 84 competitions) plus 10 sessions and a result history per athlete. Scale 3
    triples athletes and sessions.
  - **Scope:** this measures our JS only, not layout or paint.
- **Chrome:** headless Chrome over the DevTools protocol with `Emulation.setCPUThrottlingRate` 4, roughly a mid-range
  phone. It times `route()` inside the real page (median of 9 runs), before (`main`) and after the fixes, at scale 1.

## What was slow, and the fixes (on `dev/noa/perf`)
1. **A new formatter on every call.** `today()`, `fmt()`, `fmtShort()` (app.js) and `ilDate()`, `hhmm()` (day.js)
   each built a new `Intl.DateTimeFormat` or called `toLocale*` with options. Building a formatter costs far more
   than using one. They are now module constants (`IL_DAY`, `FMT`, `FMT_SHORT`, `HHMM`); the output is unchanged.
2. **`today()` inside a filter.** `upcoming()` called `today()` once per competition; it now calls it once.
3. **`upcoming()` inside a sort comparator.** `#sports` called `upcomingIn()` on both sides of every comparison:
   about 33·log 33·2 calls, each filtering 84 competitions and calling `today()` 84 times. The first start per sport
   is now computed once, before the sort.
4. **`compOn()` for every athlete on every day.** `fallbackSessions(d)` matched every athlete to a competition before
   checking whether she has anything that day. The empty `#day` looks ahead up to 120 days, so that was 120 × athletes ×
   competitions. It now skips athletes with no result and no `nextDate` on that day.

Smoke tests pass unchanged; all four are pure refactors.

## Indexes (on `dev/noa/perf-indexes`)
`memoOn(sources, build)` (app.js) rebuilds an index only when one of its source arrays is replaced. Every data
load, public or live, replaces `S.athletes`, `S.sports`, `S.comps` and `S.quotas` wholesale, and nothing mutates
them in place, so there are no invalidation hooks to forget. A smoke test covers replacement.

| Index | Used by |
|---|---|
| sport by id, athlete by id | `sportById()`, `sportName()`, new `athleteById()` |
| athletes by sport, quotas by sport | `athletesOf()`, `quotasOf()` (they return copies, since callers sort them) |
| competitions by sport | `compOn()` |
| sessions, validated once, by Israel day | `exportedSessions()`, `daySessions()` |
| athletes by `nextDate` or result day | `fallbackSessions()` |

## Proposed next (not done here)
- **The remaining `toLocale*` calls.** Month headings, `dayTitle`, the strip chips and the freshness line still build a
  formatter per call. They are cheap at today's call counts; switch them to constants when those files change anyway.
- **`#calendar` is HTML-bound.** 48 KB of markup and 32 ms throttled, mostly building strings for every future
  competition. Past competitions are already hidden by default. If it grows, collapse months after the next three
  into `<details>`.

## How to re-run
`node tests/bench.js 1 3` (or `BENCH_ONLY=sports,today node tests/bench.js 3` for some routes). It isn't part of CI:
timings vary by machine, so compare before and after on the same machine.
